# 硬件利用率分析（A2 档，统一表 + EC + dedup）

采样：8 die 跑 A2 档（global 16,384）600 步，**宿主侧** `npu-smi info -t usages` 每 2 s 采 8 卡，共 15 轮；同窗口无 profiler 步时 **15.45 ms / 1,037,877 sps**。

## 1. 实测占用

| 指标 | 均值 | 峰值 |
|---|---:|---:|
| AICore 使用率 | **2.9%** | 14% |
| AIVector 使用率 | **0.6%** | 3% |
| AICPU 使用率 | 0.1% | 1% |
| DDR/HBM 带宽使用率 | **0%**（采样精度以下） | 0% |

对照 profile 口径（同一配置，20 步窗口）：**计算类活跃 6.62 ms / 25.2 ms = 26.3% wall**，空转 47.7% + 等待 32.3%。

> 两个口径不矛盾：`npu-smi` 是 2 s 粒度的瞬时占用（每步只有 15 ms，占空自然很低）；profile 是窗口内并集。判断「硬件用没用满」用前者，判断「步内时间花在哪」用后者。

## 2. 这台机器上这项负载到底需要多少算力/带宽

模型：`13 → 512 → 256 → 128`（bottom）+ 27×27 点积交互 + `857 → 1024 → 1024 → 512 → 256 → 1`（top）。

| 项 | 每样本 | 说明 |
|---|---:|---|
| 前向 MACs | ≈ 2.85 M | bottom 0.17 M + 交互 0.09 M + top 2.58 M |
| 训练 FLOPs（≈3× 前向） | **≈ 17.1 MFLOPs** | 反向按 2× 前向估 |
| 稀疏访存（dedup 后 7.7 个唯一 id） | ≈ 15.8 KB | 查表 3.9 KB + 梯度/Adagrad 累加器 11.9 KB |

按实测吞吐换算（1.038 M sps）：

| 资源 | 实际达到 | 占什么比例 |
|---|---:|---|
| 算力 | **≈ 17.7 TFLOP/s** | 需按该机型 fp32/bf16 峰值折算 MFU（本表不臆造峰值，待填） |
| HBM 流量 | **≈ 19 GB/s**（稀疏 16.4 + 稠密权重 2.7） | 与 `DDR 带宽 0%` 一致，远低于带宽上限 |

## 3. 结论

1. **硬件能力没有发挥出来，但不是算力不够**：AICore 3%、AIVector 0.6%、带宽 0%，说明设备绝大部分时间在等任务，而不是算不动。
2. 根因是**每步有效工作量太小**：单步 15–20 ms、每步数百个任务、单任务几十微秒，实测 47.7% 空转 + 32.3% 等待。
3. DLRM 的算术强度天然很低（每样本 17 MFLOPs 对 16 KB 访存），**用 MFU 衡量它本身不合适**；对这类模型应看「每步固定开销摊薄程度」。
4. 因此提升利用率的正确做法是「让每次下发带更多活」，而不是「换更快的算子」：
   - 增大每卡本地 batch（摊薄固定开销；注意无 A100 对应档，只能作利用率参考）；
   - 继续压每步任务数（dedup 已见效：A2 20.34 → 16.31 ms）；
   - dense 与 sparse 走不同 stream 重叠，把 AICore 从 3% 抬起来；
   - 不建议为了抬高 MFU 去加大 MLP/交互规模——那会改变模型语义，与 A100 对照也无意义。
