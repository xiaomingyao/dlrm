一句话：优化前 dlrm950 在 Criteo 1TB 切片上达到 A100 的 41%（16384 档 42.90 ms vs 17.70 ms）。第一轮只改"每步同步"节奏，最好只拿到 −7.1%（2048 档）/−2.6%（16384 档），且同步间隔拉到 50 步反而慢 49%。说明 12.80 ms 的 idle 不是逐步同步造成的，下一轮应转向 HKV 反向 lookup（15.05 ms/步，35%）。

3. 第一轮实验：同步节奏（P2）

做法：把每步 torch.npu.synchronize() + loss.item() + acc .item() 改为每 N 步一次（--sync-every），其余不变。

三条判据

  1. 逐步同步不是 idle 的来源：1/2/4/8 四档差异 <1.2 ms（±3%），远小于 12.80 ms 的 idle。
  2. "去掉同步" ≠ "流水起来"：同步间隔 50 步时 host 超前下发、队列积压，16384 档反而 67.43 ms（+49%），std 从 1.6 涨到 10.9 ms。
  3. 小 batch 才有收益：2048 档同步开销相对占比大，间隔 4 拿到 −7.1%；16384 档设备是瓶颈，改同步几无意义。

5. 口径与限制

  • 数据量：本机 112.3 M 行 vs A100 的 4.19 B 行/epoch；两者都是真实 Criteo 1TB 日志，但样本量差 37×。
  • 会话间波动：同一份脚本两次测量，16384 档 median 42.90 → 42.26 ms，2048 档 24.26 → 20.89 ms（含 675/740 ms 的偶发尖峰）；单次测量不足以判定 1–2 ms 级差异，需 n≥3 取中位。
  • 脚本差异：P2 用副本 dlrm_v2_train_opt.py 跑，对照同为该副本 --sync-every 1；与原始脚本的 42.90 ms 相差约 2.3 ms，属会话波动范围，未做同脚本交叉验证。
  • profile 口径：只解析 rank0 / device_0；8 rank 的 HCCL 时长会随通信量上升，占比以单 die 为准。
  • 优化器：dlrm950 稠密侧固定 SGD，A100 的 2048 档是 Adagrad，两者收敛口径不同，本报告只比速度。
