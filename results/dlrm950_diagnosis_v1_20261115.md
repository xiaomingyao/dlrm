# DLRM 在昇腾 950DT 上的性能诊断报告 v1

- **硬件**：8 die Ascend950DT（单 die HBM 96 GiB，UB 互联）· CANN 9.1.0 · 驱动/固件 25.1.rc2 / 7.0.9.100.203
- **模型**：DLRM —— bottom MLP 13→512→256→128，27×27 dot 交互，top MLP 857→1024→1024→512→256→1，26 张稀疏表
- **数据**：Criteo 1TB 切片（day0–6，训练 22,184,476 行 / 测试 2,295,467 行），MLPerf 词表 26 特征合计 268,435,456 行（fp32 约 97.4 GB）
- **对照**：官方 8×A100 40GB（Criteo 1TB，dot/SGD 与 dot/Adagrad 档）
- **口径**：每档多轮取 **median**，稳态剔除前 20 步；「端到端」= 步时 + host 取数；profiler 数据只用于看占比（扰动 1.19–1.30×）

## 1. 一页结论

| 档 | global batch | 每卡本地 | 端到端 ms | 吞吐 sps | 对 A100 |
|---|---:|---:|---:|---:|---:|
| A1 | 2,048 | 256 | 7.44 | 275,000 | **134%** |
| A2 | 16,384 | 2,048 | 16.23 | 1,009,000 | **109%** |
| A4¹ | 131,072 | 16,384 | 62.30 | 2,104,000 | **177%** |

¹ A100 的 A4 档用 DCN v2 交互，本实现只有 dot（算力需求更低），该行不是同模型对比，仅作规模参考；严格同口径的是 A1/A2 两档。

² A2 档已补跑满 epoch（1,354 步）：端到端 **16.13 ms / 1,015,600 sps = 109.7%**，与上表 300 步截断值差 0.7%，见 §5.1。

| 判断 | 依据 |
|---|---|
| **算力侧已接近极限** | MatMulV3 的 `cube_utilization` 均值 91.3%、峰值 99.5%，`aic_mac_ratio` 0.77 —— 稠密矩阵乘在 Cube 上基本打满，继续调算子没有空间 |
| **整机大部分时间空转** | 宿主 `npu-smi` 采样 AICore 2.9%、AIVector 0.6%、HBM 带宽低于采样精度；每步仅 173 个 kernel、单 kernel 数十微秒 |
| **瓶颈是「喂不饱」而非「算得慢」** | 阶段 2（A2）窗口内：通信 25%、计算 11%、wait+空隙 64%；阶段 4（A4）：通信 25%、计算 14%、其它 17%、空隙 44% |
| **950 的优势在大 batch 兑现** | 固定开销拟合 **8.33 ms + 0.361 µs/样本**；批量 16,384→131,072，每样本成本 0.897→0.432 µs，端到端吞吐翻 2.08 倍 |
| **2× 在 A2 档不可达** | A2 需 8.85 ms，当前 16.23 ms；剩余可动项上限合计（重叠 ~5 ms + 合并 collective ~1.2 ms + 其余 2–4 ms）乐观 10–11 ms |

## 2. 测试条件与测量方法

| 项 | 说明 |
|---|---|
| 并行方式 | 8 die 单机，DMP（模型并行 + 数据并行），每卡本地 batch = global/8 |
| 表放置 | 26 张稀疏表合 1 张统一表（各特征 id 区间互不重叠），行数 268,435,456，按行切分到 8 die，每卡 HBM 约 12 GiB |
| 优化器 | 稠密侧 SGD；稀疏侧 Adagrad（row-wise） |
| 步时定义 | forward + backward + optimizer.step；起点取「拿到本步数据之后」，每步 `synchronize` 后计时 |
| 取数 | numpy 切片 → 转 tensor → H2D；单独计时并单列，不混入步时 |
| 噪声 | 节点为多租户，同一配置不同批次波动 ±8~12%；结论均用交错多轮取 median，单次只作方向判断 |
| profiler | 阶段 0/1 用 `msprof`（含 AICPU、SDMA）；阶段 2/3 用 `torch_npu.profiler`（该配置下 msprof 段错误）。两套工具口径不同，跨阶段只比占比、不比绝对值 |

## 4. 硬件利用率

### 4.1 算子级

| 指标 | A2 档 | A4 档 | 含义 |
|---|---:|---:|---|
| MatMulV3 `cube_utilization` | 91.3%（峰 99.5%） | ≈91% | Cube 阵列大多数时间在做 MAC，算子实现接近理论 |
| MatMulV3 `aic_mac_ratio` | 0.77 | ≈0.77 | MAC 占 Cube 时间 77%，其余为取数/写回 |
| 矩阵乘占窗口 | 2.4 / 21.5 = 11% | 10.26 / 73.7 = 14% | 稠密侧本身不是主要开销 |
| 通信占窗口 | 25% | 25% | all2all 为主（26 特征已打包成 1 特征） |
| wait + 空隙 | **64%** | **44%** | 设备等前驱/等对端，是最大浪费 |

> `kernel_details.csv` 只含 AI Core / AIV 任务，不含 AICPU 与 SDMA，故各类并集相加小于设备实际忙时；绝对忙时以 msprof task_time 口径为准（阶段 1：设备忙 13.2 ms / 窗口 25.2 ms = 52.3%）。

### 4.2 整机级（宿主 `npu-smi` 采样 8 卡）

| 采样方式 | AICore 均值 | 峰值 | 说明 |
|---|---:|---:|---|
| 训练对齐（等日志出现 `ep0 step` 后再采，0.5 s 间隔） | **4.84%** | 17% | 只覆盖训练窗口，口径正确 |
| 早期采样（进程启动后 35 s 起采 30 s） | 2.9% | 14% | **⚠️ 作废**：该窗口覆盖数据加载与收尾阶段，训练只占其中约 20 s，均值被稀释 |

> **口径更正**：先前报告里的「AICore 2.9%」采样窗口未与训练对齐（A2 档 1354 步只要约 20 s，而建表 + 加载要约 30–40 s），因此不能代表训练时的占空。以训练对齐的 4.84%（峰值 17%）为准；早期 2.9% 不再引用。

理论占空（可与实测对照）：A2 档矩阵乘 1.46 ms / 窗口 21.5 ms = **6.8%**，其中 Cube 忙 91.3% ⇒ 预期 AICore 占空约 **6.2%**；实测 4.84%，差值是矩阵乘之间的等通信间隙与采样相位误差。

其它整机指标（同期采样）：AIVector 0.6%（峰值 3%）、AICPU 0.1%、HBM 带宽 0%（= 峰值的 0.27%，标定见 §4.5）。

### 4.3 折算到物理量

| 项 | A2 档 | A4 档 | 算法 |
|---|---:|---:|---|
| 每样本训练算力 | 17.1 MFLOPs | 17.1 MFLOPs | 前向 2.85 M MAC（bottom 0.17 M + 交互 0.09 M + top 2.58 M）× 2 × 3 |
| 达成算力 | 19.0 TFLOP/s | 39.5 TFLOP/s | 吞吐 × 17.1 MFLOPs |
| 每样本稀疏访存 | 15.8 KB | 15.8 KB | dedup 后 7.7 个唯一 id × 128 维 × 4 B ×（查 1 + 梯度 1 + Adagrad 累加 2） |
| HBM 流量 | ≈19 GB/s | ≈37 GB/s | 吞吐 × 15.8 KB + 稠密权重往返 |

> MFU 需要该机型 fp32/bf16 峰值，本报告不臆造；用 `cube_utilization` 91.3% 判断算子效率更直接：算子已接近理论上限，整机占用低是「没活干」，不是「干得慢」。

## 4.4 Embedding 表与 HBM 占用

统一表模式下只有 1 张表（26 个特征的 id 区间平铺，互不重叠）：

| 项 | 值 |
|---|---:|
| 行数（2 的幂对齐后） | **268,435,456** = 2²⁸ |
| 行数（各特征原始基数之和） | 204,222,464 |
| 每行维度 | 128（fp32） |
| 表本体总量 | **128 GiB**（137.4 GB） |
| **单 die 占用（8 die 行切分）** | **16 GiB** |
| Adagrad 状态（每行 16 个 float） | 16 GiB 总 / 2 GiB 单 die |
| **embedding 侧单 die 合计** | **≈18 GiB / 96 GiB（19%）** |

- **对齐浪费**：204.2 M 行向上取到 2²⁸ 行多出 64,212,992 行，等于白占 **32 GiB**（31.4%），单 die 4 GiB。对应待验证项 O11（`--unified-align batch` 已实现，未上机）。
- **基数分布**：f0 / f9 各约 4,000 万行，f10 306.8 万，f11 40.5 万，其余多为千到万级 —— 前 3 个特征占约 40% 的行，这也是原始 26 表时每步要发 24 次查表的根源。
- **对优化的含义**：表只占单 die HBM 的 19%，所以能把 batch 一路加到 131,072（O14 曲线的基础）；HBM 带宽折算仅约 19 GB/s，说明瓶颈不在访存，换 bf16 values（表减半到 8 GiB/die）也换不来性能。


## 4.5 HBM 带宽为什么显示 0%

**结论：计数器正常，0% 是真实读数** —— 本负载的 HBM 流量只占单 die 峰值带宽的千分之几，`npu-smi` 只给整数百分比，亚 1% 一律显示 0。

### 4.5.1 先标定计数器（同一台机器实测）

用纯拷贝把带宽打满，同时读 `npu-smi`：

| 探针 | 实测带宽 | `npu-smi` HBM 带宽 | `npu-smi` AICore |
|---|---:|---:|---:|
| `copy_` 2 GiB 张量 × 11,000 次（14.26 s） | **3,313 GB/s** | **76–77%** | 99% |
| `add` 2 GiB（out=） | 4,738 GB/s | — | — |

⇒ 反推该 die 的 100% ≈ **4,300 GB/s**；计数器既能读到 0 也能读到 77%，说明它没有失效，同时 AICore 计数也正常（拷贝期间 99%）。

### 4.5.2 DLRM 实际流量折算（每 die 每步）

| 项 | 每步字节 | 依据 |
|---|---:|---|
| 稀疏查表（dedup 后） | ≈2.4 MB | 2,048 样本 × 7.7 唯一 id ×（读 512 B + 梯度写 512 B + Adagrad 读写 128 B） |
| 稠密权重往返 | ≈41 MB | 3.40 M 参数 × 4 B × 3 遍（前向 / 对输入梯度 / 对权重梯度） |
| 激活值存取 | ≈130 MB | 每样本约 21 KB（857 + 512/256/128 + 729 + 1024/1024/512/256）× 2,048 × 约 3 遍 |
| **合计** | **≈173 MB / 15 ms ≈ 11.5 GB/s** | 占 4,300 GB/s 的 **0.27%** |

0.27% 在整数百分比下就是 **0%**。即使把全部激活算错一半，也仍在 0.1–0.5% 量级，显示不出非零值。

### 4.5.3 为什么这么小

- 查表已被 dedup 压到 **7.7 个唯一 id/样本**（原 42.6 万 key/步 → 12.6 万），稀疏侧几乎不产生流量。
- 稠密侧权重只有 3.40 M 参数（13.6 MB），一个 step 走三遍也才 41 MB。
- 所以这台机器的 HBM 带宽完全不是约束 —— **瓶颈是延迟与同步**（wait + 空隙 64%），不是搬不动数据。这也解释了为什么 bf16 化（表减半、流量减半）换不来性能（O15：+16% 更差，cast kernel 反而增加开销）。


## 5. 扩展性：固定开销与每样本成本

| global batch | 每卡本地 | 步时 ms | 取数 ms | 端到端 ms | 吞吐 sps | 每样本 µs |
|---:|---:|---:|---:|---:|---:|---:|
| 2,048 | 256 | 6.92 | 0.52 | 7.44 | 275,000 | 3.63 |
| 16,384 | 2,048 | 14.70 | 1.53 | 16.23 | 1,009,000 | 0.99 |
| 32,768 | 4,096 | 21.30 | 2.99 | 24.29 | 1,349,000 | 0.74 |
| 65,536 | 8,192 | 29.52 | 7.24 | 36.76 | 1,783,000 | 0.56 |
| **131,072** | 16,384 | 56.60 | 5.70 | 62.30 | **2,104,000** | 0.47 |

最小二乘拟合（16k–131k 四点）：**步时 = 8.33 ms + 0.361 µs/样本**，残差 +0.45 / +1.13 / −2.49 / +0.91 ms，与「固定开销 + 线性增长」吻合。固定项 8.33 ms 对应：HCCL 发射 1.23 + alltoall 固定延迟 + 每步同步/下发开销。

取数在 65k 档（7.24 ms）偏高属 host 抖动（同批 131k 仅 5.70 ms），说明取数不是瓶颈但需要固化（加载期一次性 log1p + dtype，训练期只切片）。

### 5.1 满 epoch 复测（1 epoch = 1,354 步，A2 档）

此前各档均为 150/200/300 步截断；补跑完整 epoch 后（训练 1 轮，测试集 day6）：

| 项 | 值 |
|---|---:|
| 步数 | 1,354（= 22.18 M / 16,384，正好 1 epoch） |
| 步时 median / mean | **14.99 / 15.38 ms**（min 13.15，max 27.42，std 1.50） |
| 取数 median / mean | 1.14 / 1.25 ms |
| 端到端 | **16.13 ms** → **1,015,600 sps** = A100 的 **109.7%** |
| 测试 AUROC | **0.7657**（随机 0.5） |
| 测试 ACC | 0.9674（全负基线 0.9679 —— acc 不可用，仅列不判） |

与 300 步截断的 1,009,000 sps 相差 0.7%，说明此前锚定值与满 epoch 一致，**吞吐结论不依赖截断步数**。AUROC 0.7657 高于 300 步时的 0.7430，属训练更充分（步数 ×4.5），不是配置差异。


## 6. 瓶颈归因

### 6.1 已坐实

- **查表不再是瓶颈**：24 次调用（15.05 ms）→ 1 次调用（0.081 ms），统一表 + dedup 共同作用。
- **通信占比稳定 25%**：每步 5 次 all2all（约 18.5 ms @A4），另有 6 次 HcclLaunch 共 1.23 ms 纯发射开销。
- **wait + 空隙是最大单项**：A2 64%、A4 44%，来源是 kernel 之间等前驱、等对端 rank、host 下发断档。
- **算子侧无空间**：Cube 91.3%，MAC 比 0.77。

### 6.2 推测（未坐实）

- **【推测】** A4 档 all2all 出现约 100 个形状特化 kernel 实例名，说明分块大小随 dedup 后唯一 id 数变化，可能触发按形状重编译/重下发；若把计数对齐到固定 bucket，可减少发射与调度开销（估计 4–6 ms），需改 dynamic_emb 内部，未验证。
- **【推测】** 各 rank 的 dedup 后 id 数不均衡，导致 all2all 出现 straggler；这是 wait 的一部分来源，尚未取到逐 rank 分布。

## 7. 剩余空间量化

| 可动项 | 上限 | A2 现值 | 说明 |
|---|---:|---|---|
| 通信与计算重叠 | ~5 ms | 已试 −4%（单次） | bottom MLP 独立 stream；A4 无收益（bottom 太小） |
| 合并 collective（6 次发射 → ≤2） | ~1.2 ms | 1.23 ms | 纯 launch 开销 |
| 减少 all2all 实例 / 计数对齐 | 4–6 ms | 18.5 ms（A4） | 需改 dynamic_emb，属侵入改动 |
| rank 间负载均衡 | 2–4 ms | 未知 | 需先取逐 rank dedup 计数 |
| 算子优化 | **≈0** | Cube 91.3% | 已无空间 |

乐观合计 10–11 ms（A2 端到端），约 1.5× 当前、1.6–1.7× A100，仍达不到 2×（8.85 ms）。结构性原因：每卡每步只有 2,048 行，固定开销 8.33 ms 占 51%。

## 8. 已验证无效（避免重复投入）

| 项 | 结论 | 实测 |
|---|---|---|
| 逐步同步节奏（sync 1/2/4/8/50） | 无效 | 差异 <1.2 ms；sync=50 反而 +49% |
| dist-type roundrobin | 无效 | A1 +8.6%、A2 +1.8%（n=3 推翻单次 −3.7%） |
| hbm-gb 加大 / frozen-data | 无效 | 仅作诊断用途 |
| all2all 载荷 bf16（qcomm codec） | 变差 | 64k 档 29.52 → 34.23 ms（+16%） |
| HCCL_OP_EXPANSION_MODE=AIV | 无效 | A4 57.78 → 58.52 ms（漂移内） |
| HCCL_BUFFSIZE=1024 | 显著变差 | A4 57.78 → 67.29 ms（+16%） |
| 整步 NPUGraph 捕获 | 不可行 | dynamic_emb 稀疏路径含 H2D 拷贝，报 107030 |
| TASK_QUEUE_ENABLE=2 | 小 batch 有效 | A2 +2.7%（均值 +7%）；A4 −2.9% ⇒ 按档选 |
