# DLRM 在昇腾 950DT（TorchRec V2 栈）上的性能报告：HKV / TBE 双实现 vs 8×A100

本报告合并「优化报告 v1/v2」与「性能诊断报告」，并按三方重写对比章：950 侧两个实现（HKV 动态表 / RecSDK TBE 静态表）与 8×A100，共 11 章。

> **v6 变更（2026-11-20）**：目标口径由「2× A100」改为 **1.5× A100**，复核环境明确为 **昇腾 950DT ×8 + TorchRec V2**；新增 §1.1（目标表 + 复核判据 + GPU 对照实现地址），§1 判断行、§3.4 差距表、§8 结论按 1.5× 重读。**实测数字一个未改**，2× 目标作为阶段二参考保留。

> **v5 变更（2026-11-20）**：全表补 **吞吐 samples/s**（本就有的列按原值保留）与 **batch/s**（每秒步数）两列，新增 §4.1 收益吞吐口径；原始 ms、百分比、结论一律未改。换算关系：`samples/s = global batch ÷ 时延`、`batch/s = 1000 ÷ 时延(ms)`。

- **硬件**：8 die Ascend950DT（单 die HBM 96 GiB，UB 互联）· CANN 9.1.0 · 驱动/固件 25.1.rc2 / 7.0.9.100.203
- **模型**：bottom MLP 13→512→256→128 + 27×27 dot 交互 + top MLP 857→1024→1024→512→256→1 + 26 张稀疏表（HKV 动态表）
- **数据**：Criteo 1TB 切片（day0–6；训练 22,184,476 行 / 测试 2,295,467 行），MLPerf 词表 268,435,456 行
- **对照**：8×A100 40GB（同数据、同 dot 交互、同每卡本地 batch；A4 档 A100 侧为 DCN v2）

## 2. 评测条件与口径

| 项 | 说明 |
|---|---|
| 并行方式 | 8 die 单机 DMP（模型并行 + 数据并行），每卡本地 batch = global/8，两侧一致 |
| 表放置 | 26 表合 1 张统一表（id 区间互不重叠），行数 268,435,456，按行切分到 8 die |
| 优化器 | 稠密 SGD；稀疏 Adagrad（row-wise） |
| 步时 | forward + backward + optimizer.step；起点为「拿到本步数据之后」，每步 synchronize 后计时 |
| **端到端** | **步时 + host 取数**（numpy 切片 → tensor → H2D）。A100 官方口径含取数，故对外一律给端到端 |
| 统计 | 多轮取 median，稳态剔除前 20 步；单次值只作方向判断 |
| 噪声 | 多租户节点，同配置不同批次波动 ±8~12%；A/B 一律交错多轮 |
| profiling | 阶段 0/1 用 msprof（含 AICPU/SDMA）；阶段 2/3 用 torch_npu.profiler（该配置下 msprof 段错误）；扰动 1.19–1.30×，只看占比 |
| 换算 | 每样本训练算力 17.1 MFLOPs；稀疏访存 15.8 KB/样本 |
| **吞吐 samples/s** | `global batch ÷ 该行时延`。**8 die 合计，不是单卡**（单卡除以 8）；A100 锚同为 8 卡合计 |
| **吞吐 batch/s** | `1000 ÷ 时延(ms)`，即每秒步数；恒等于 `samples/s ÷ global batch`。升 batch 时 batch/s 下降属正常 |

### 3.5 950-TBE（RecSDK dlrm）实测

同 8 die、同一份 Criteo 1TB 切片（112.3 M 行，MLPerf 词表约 104 GiB 静态 TBE），RecSDK 版**未做任何优化**（仅跑通基线）。其交互为 MLPerf DCN v2、稀疏与稠密均 Adagrad，与本实现（dot）不同，故与 A100 只能按同交互对齐。

| 实现 | local / global | 交互 / 优化器 | 步时 | 吞吐 sps | **batch/s** | AUROC |
|---|---|---:|---:|---:|---:|---:|
| recsdk-dlrm（TBE） | 256 / 2,048 | DCN v2 / Adagrad | 278 ms | **7,356** | **3.60** | 0.6945 |
| recsdk-dlrm（TBE） | 2,048 / 16,384 | DCN v2 / Adagrad | 261 ms | **62,690** | **3.83** | 0.7525 |
| 8×A100（同配置） | 2,048 / 16,384 | DCN v2 / Adagrad | 18.2 ms | 901,120 | 54.95 | — |
| **达成率（对 A100 同配置）** | 16,384 档 | — | — | **7.0%** | **7.0%** | — |

- **固定开销主导**：255–285 ms/步，与 batch（256 vs 2,048，差 8 倍）和表规模都几乎无关；1 die 上同样复现 185 ms ⇒ 不是通信带宽问题，而是 26 张表各自的算子链 + 每步 collective 的串行开销。
- **横向对照**：同一台 950、同一份数据、同 local batch 下，HKV 版 62,690 → 1,015,600 sps（16.2×），256 档 7,356 → 275,000（37.4×）。
- **不能得出的结论**：这 16–37× 混合了「交互不同（dot vs DCN v2）」「表机制不同（HKV 动态物化 vs 静态 TBE 全驻）」「优化器不同」「数据量不同（24.5 M vs 112.3 M 行）」四个变量，只能作为同机工程对比，不能拆成单一因素归因。

### 4.1 收益的吞吐口径（samples/s 与 batch/s）

收益不只看 ms，按吞吐再看一遍（数值由各行原始 ms 换算，未引入新测量）：

| 编号 | 优化项 | 档 | 前 → 后 ms | Δ% | samples/s 前 → 后 | batch/s 前 → 后 | 口径 |
|---|---|---|---:|---:|---:|---:|---|
| O6 | 统一表（26→1） | A1 · 2,048 | 21.192 → 6.781 | −68.0% | 96,640 → **302,020** | 47.19 → **147.47** | 纯 step，n=3 |
| O6 | 统一表（26→1） | A2 · 16,384 | 40.269 → 20.342 | −49.5% | 406,864 → **805,427** | 24.83 → **49.16** | 纯 step，n=3 |
| O7b | EC + index dedup | A2 · 16,384 | 20.342 → 16.309 | −19.8% | 805,427 → **1,004,599** | 49.16 → **61.32** | 纯 step，n=3 |
| O7b 反例 | 同配置用在 A1 | A1 · 2,048 | 6.781 → 9.890 | +45.8%（变慢） | 302,020 → **207,078** | 147.47 → **101.11** | 纯 step，n=3 |
| O12 | 取数固化（log1p + dtype） | A4 · 131,072 | 12.46 → 5.70 | −54.3% | 10,519,422 → **22,995,088** | 80.26 → **175.44** | **取数段**，非步时 |
| O14 | 本地 batch 16,384 → 131,072 | A2 → A4 | 16.23 → 62.30 | 吞吐 2.08× | 1,009,489 → **2,103,884** | 61.61 → **16.05** | 端到端（跨档） |

三条读法：

1. **O14 那行 batch/s 是降的**（61.61→16.05）：batch 大 8 倍、每秒步数降 3.8 倍，吞吐仍升 2.08× —— 判吞吐看 samples/s，不看 batch/s。
2. **O12 是取数段口径**（prep 12.46→5.70 ms），其 22.99 M sps 只描述取数段等效，不能与整步吞吐并列。
3. **纯 step 与端到端不互算**：本表 O6/O7b 为纯 step，O14 为端到端；A2 的端到端主口径见 §3.1（16.13 ms→1,015,600 sps→62.00 batch/s）。

## 7. 归因

### 7.1 已坐实

- 查表不再是瓶颈：24 次（15.05 ms）→ 1 次（0.081 ms）。
- 通信稳定 25%：每步 5 次 all2all（@A4 ≈18.5 ms）+ 6 次 HcclLaunch 1.23 ms 纯发射。
- wait + 空隙最大：A2 64%、A4 44%。
- 算子无空间：Cube 91.3%、MAC 比 0.77。
- 带宽无空间：0.27% 占用；bf16 化更慢（O15 +16%）。
- TBE 侧瓶颈是每步固定开销：255–285 ms 与 batch、表规模无关（1 die 185 ms）⇒ 26 张表算子链 + 每步 collective 串行；HKV 批量化查表后 15 ms，是 16–37× 差距主因（§3.5）。

### 7.2 推测（未坐实）

- 【推测】A4 档 all2all 约 100 个形状特化 kernel 名，说明分块随 dedup 后 id 数变化，可能触发重编译/重下发；计数对齐可减 4–6 ms。
- 【推测】各 rank dedup 后 id 数不均衡导致 all2all straggler，是 wait 来源之一；未取逐 rank 分布。

## 8. 剩余空间与下一步

| 可动项 | 上限 | 当前 | 前置条件 |
|---|---:|---|---|
| 通信与计算重叠 | ~5 ms | 已试 −4%（单次） | 需 n=3；A4 无效 |
| 减少 all2all 实例 | 4–6 ms | 18.5 ms（A4） | 改 dynamic_emb |
| rank 间负载均衡 | 2–4 ms | 未知 | 先取逐 rank 计数 |
| 合并 collective | ~1.2 ms | 1.23 ms | 收益已很小 |
| 算子优化 | ≈0 | Cube 91.3% | — |

合计乐观 10–11 ms（A2 端到端）≈1.5× 当前、1.6–1.7× A100，仍不到 2×（8.85 ms）。结构性原因：每卡每步仅 2,048 行，固定开销 8.33 ms 占 51%。

**按 1.5× 目标重读（2026-11-20）**：A2 只需 **−4.33 ms**（16.13 → ≤11.80 ms，即 **≥1,388,544 sps / ≥84.75 batch/s**）、A1 只需 **−0.77 ms**（7.44 → ≤6.67 ms，即 **≥307,200 sps / ≥150.00 batch/s**）、A4 已达标（62.30 ms = 2,104,000 sps / 16.05 batch/s；目标 ≤73.42 ms = 1,785,192 sps / 13.62 batch/s，余 11.12 ms）。即 10–11 ms 的乐观上限里只要落地**不到一半**即可覆盖 1.5×；但 A2 的 4.33 ms 必须来自真实 kernel/通信改动（P1 查表、P4 collective 合并），单纯调参已被 §9 全部排除。2× 仍属结构性目标。
